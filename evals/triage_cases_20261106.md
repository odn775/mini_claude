## 用例 1：普通症状 → 科室推荐（回归）

**输入**

```
最近三天咳嗽有痰，不发烧
```

**期望**：主推 **呼吸内科**，紧急程度普通门诊，依据引用「咳嗽有痰三天」。

**实际**：通过。工具序列 `search_knowledge → recommend_department`；返回
`呼吸内科 / routine`，依据「用户'最近三天咳嗽有痰，不发烧'，符合呼吸内科'咳嗽、咳痰持续 3 天以上'」，
advice 提示记录痰的性状、携带胸片/CT 报告。索引重建后旧文档未丢失。

## 本轮发现的三个问题

1. **知识覆盖缺口**：缺 `心血管内科.md`，胸痛类主诉只能靠其他文档的鉴别段落兜底。
   建议补一份，覆盖心悸、胸闷、高血压、下肢水肿等症状。
2. **用量记录不全**：5 轮对话在 `usages` 表里只有 4 条（06:15:04 / 06:17:18 / 06:18:32 / 06:19:16），
   缺一轮。若某轮没有收到 `usage` 事件就不会落库，需要确认是哪一轮、是否影响统计完整性。
3. **消息时间戳失真**：`messages` 表所有行的 `created_at` 都是同一秒（06:19:15/16），
   因为每轮结束会整份重写消息表（历史压缩需要），时间戳随之刷新。
   论文里要写「每轮耗时」只能取 `usages.latency_ms`，不能用消息时间戳。

## 补充：CLI 与 Web 的数据库关系

两端**不是分开的库**：`backend/.env` 的 `DATABASE_URL` 指向 `127.0.0.1:3306`，
与容器内 MySQL 是同一实例（端口已映射到本机回环）。CLI 写入的会话 `source='cli'`，
Web 侧栏能看到并带 `CLI` 标记。

CLI「看不到数据库里的数据」是**缺少查看入口**：当前 CLI 只有 `/clear`、`/compact`、
`/context` 等命令，没有「列出历史会话」或「续接历史」的功能，每次启动都新建会话。
若要两端行为对齐，需要给 CLI 加 `/sessions` 与续聊能力（本轮未做）。
